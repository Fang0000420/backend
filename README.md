# Campus Activities Backend · 校园活动报名与票务系统

基于 Java、Spring Boot 和 MyBatis-Plus 的校园活动后端项目。围绕活动发布、用户报名、名额管理和通知，逐步实现权限控制、数据库事务、并发处理、缓存、消息队列和部署运维。

项目采用单体应用起步，以免费活动为主，不接入真实支付。各阶段按照功能和测试结果验收，逐步增加依赖。


## 本地运行

### 1. 准备环境与数据库

- 安装 JDK 21 和 MySQL，首次构建需要网络下载依赖。
- 准备 `activity` 数据库及与实体匹配的 `activity` 表。
- **仓库尚未提供建表脚本。** 新环境需先取得现有表结构；仅创建空数据库无法完成业务查询。后续将补充版本化建表与迁移文件。

```bash
git clone https://github.com/Fang0000420/backend.git
cd backend
```

### 2. 配置数据库连接

在 `src/main/resources/` 下新建 `application-local.yml`。当前 `.gitignore` 已忽略这个文件，文件名应保持一致。

建议使用以下配置，并在 IDEA 运行配置或本机环境中设置 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD`：

```yaml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
```

本地 URL 示例：`jdbc:mysql://localhost:3306/activity?serverTimezone=UTC`。按实际环境设置数据库地址、账号和连接选项。数据库时间与接口时间的统一约定将在 M1 明确。

使用具有所需权限的应用账号，不提交实际密码、云密钥或包含这些内容的日志。已经公开过的有效凭据需要更换，仅从后续提交中删除不能使旧凭据失效。

### 3. 启动应用

macOS / Linux：

```bash
sh mvnw spring-boot:run
```

Windows：

```powershell
.\mvnw.cmd spring-boot:run
```

也可以在 IDEA 中运行 `BackendApplication`。默认端口为 `8080`，接口文档位于 [Swagger UI](http://localhost:8080/swagger-ui/index.html)，OpenAPI 描述位于 [API Docs](http://localhost:8080/v3/api-docs)。

```bash
curl -i http://localhost:8080/api/activity
```

### 4. 构建与测试

```bash
# 编译源代码
sh mvnw compile

# 执行测试：需先准备测试所依赖的配置和数据库
sh mvnw test

# 执行测试并打包
```

当前尚未提供独立测试数据库配置，`contextLoads` 也不等于业务验收测试。后续数据库测试使用独立测试库或测试容器。

### M2：可靠报名与取消

**功能需求**

- [ ] 登录用户可报名已发布且未开始的活动，每次报名占一个名额；名额不足时拒绝。
- [ ] 报名订单包含 `CONFIRMED`、`CANCELLED` 两种状态；用户仅可查询、取消自己的订单。
- [ ] 扣减名额与创建订单在同一数据库事务中完成，共同成功或回滚。
- [ ] 同一用户对同一活动最多创建一笔订单；本期取消后不支持重新报名。
- [ ] 同一报名请求重复提交返回同一业务结果；同一请求标识用于不同参数时拒绝。
- [ ] 首次取消归还一个名额，重复取消不重复归还；活动发布后本期不修改总名额。
- [ ] 使用数据库约束及明确的并发控制策略，保证剩余名额不为负。

**验收标准**

- 10 个名额报名 1 人后，剩余 9，有效订单 1。
- 扣名额后故意抛异常，订单和名额共同回滚。
- 顺序或并发重复请求只创建一笔订单、只扣减一次名额。
- 20 个不同用户竞争 10 个名额，最终成功订单不超过 10，且剩余名额 + 有效报名人数 = 总名额。
- 重复取消不增加额外名额，用户 A 无法读取或取消用户 B 的订单。
- 保存并发设置、响应统计和数据库核对结果，说明单次测试的覆盖范围。

- [ ] 日志不记录密码、会话凭据等敏感信息，管理接口限制访问范围。

**验收标准**

- 同一统计日期重跑结果一致，失败后的恢复不会重复计数。
- 能用同一请求标识串联接口与业务日志。
- 模拟慢数据库请求或线程池拥堵，根据日志和指标定位原因，并记录调整前后的数据。

### M6：可重复构建与部署

**功能需求**

- [ ] 提供 Docker 镜像构建和 Docker Compose 配置，明确应用与所需中间件的启动顺序。
- [ ] 提供数据库迁移、开发测试数据初始化和多环境配置说明。
- [ ] 将构建与测试接入自动化流程，失败时阻止交付。
- [ ] 提供健康检查、日志查看、版本更新与失败回退步骤。
- [ ] 数据库测试与真实业务数据隔离，至少使用真实 MySQL 或 Testcontainers 验证事务和锁行为。

**验收标准**

- 在干净环境中按 README 完成启动，并执行主要接口验收。
- 自动化流程可以报告测试失败，不通过跳过测试掩盖问题。
- 实际演示一次版本更新与回退，说明数据迁移对回退的限制。

### M7：AWS 部署扩展

**功能需求**

- [ ] 将同一应用部署到 EC2，通过 VPC、子网和安全组明确访问路径。
- [ ] 使用 RDS for MySQL 保存业务数据，验证应用到数据库的连接。
- [ ] 使用 S3 存储活动封面，明确上传、读取及访问授权规则。
- [ ] 将运行日志接入 CloudWatch，并配置必要的监控与告警。
- [ ] 使用适当的 IAM 角色和最小权限，明确配置与凭据来源。
- [ ] 记录资源费用、预算控制和资源清理步骤。

**验收标准**

- 云端可演示已完成的核心流程，应用重启后业务数据保留。
- 能解释客户端到应用、数据库和对象存储的请求路径及权限边界。
- 能通过云端日志定位一次故障，并演示资源清理。

ECS 容器部署、SQS 适配、微服务拆分和复杂前端作为后续选做，不作为上述阶段的前置条件。

## 开发与验收约定

- 每次完成一个小功能，提交代码和对应验证结果，再推进下一步。
- 自动化测试、手动请求截图、代码审阅分别记录；“能编译”不等于“业务已通过”。
- 数据库约束、默认值和索引以版本化 SQL 或迁移文件为准。
- API 的成功与失败响应保持稳定；接口或规则变化时同步更新文档与测试。
- 每个阶段记录所用资料或 AI 协助，以及能够独立解释、修改的部分。
